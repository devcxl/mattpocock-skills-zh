# 编写文档页面

`engineering/` 和 `productivity/` 中的每个技能在 `docs/<bucket>/<skill-name>.md` 都有一份面向人类的**文档页面**：文档树镜像 `skills/` 下的这两个 bucket 文件夹。它发布在 `https://aihero.dev/skills-<skill-name>`；URL 始终是 `skills-<skill-name>`，与 bucket 无关，因此文档路径只是仓库组织形式。页面不是技能，也不是 `SKILL.md` 的副本。只有这两个 bucket 是晋升的；其余（`misc/`、`in-progress/`、`deprecated/`）没有文档页面。

这些技能大多是**用户调用**的：agent 不会替你触发它们，所以*你*要记得它们的存在和触发时机。这份记忆就是**认知负载**。文档页面的工作就是把它卸下来：围绕一项技能把读者安顿好，让他们能在脑中记住它，知道何时使用它，并看到它在系统中的位置。这些页面合起来是一个分布式路由器；每页都是一个节点。

每当一个晋升的技能被新增、重命名或行为发生变更时，请执行：创建或重新同步其文档页面。重命名也会移动文件（`docs/<bucket>/<old>.md` → `docs/<bucket>/<new>.md`），因为发布的 URL 跟随技能名；一个在 `engineering/` 和 `productivity/` 之间迁移的技能，其文档文件也会搬到对应的文件夹。`misc/`、`in-progress/` 和 `deprecated/` 中的技能没有页面：这些 bucket 都不晋升。一个技能*从*这些 bucket 之一迁入 `engineering/` 或 `productivity/`，会获得一个页面；向相反方向迁移则失去页面。

由于这些页面发布在 `aihero.dev` 上，**每个链接都是绝对的**：绝不要使用仓库相对路径。指向另一个技能的链接指向 `https://aihero.dev/skills-<name>`；指向仓库的链接使用完整的 `https://github.com/mattpocock/skills/...` URL。在仓库中有效的相对链接一旦发布就会失效。

没有 H1：发布后的页面从 slug 中取得标题。

## 页面结构

按下面的模板填充，保持顺序。**固定结构**（`## 它的作用`、`## 何时使用`、`## 它的定位`）每页都出现。`## 先决条件` 与自由形式的内容部分只承载这个特定技能需要的内容；其余删掉。

四个部分决定一页是否值得读：`它的作用`、`何时使用`、`常见问题`、`怎样算成功`。前两个负责把读者安顿好；后两个是页面从"概述技能"转向"回答读者自己的处境"的地方。后两个各有一道门槛，下面会说：把门槛两边都过不了的页面视为未完成，而不是"完成了但短"。

**页面不写任何安装命令。** ai-hero 的页面模板在正文之上自行渲染安装小组件：复制按钮、单一技能命令、整套命令、更新命令：而页面里再写一遍会让读者看到同一命令两次，两份副本还会漂移：每页手写的两条命令已经和它旁边的组件对不上了。安装文案属于站点，不属于页面。如果要改，改 ai-hero；标准文案见[安装块](./install-block.md)。

## 它的作用

一两段通俗语言。以技能的一句话职责开头，再陈述**定义性约束**：使这个技能不同于显而易见默认行为的那一条事实（以 `to-spec` 为例：它不再对用户做访谈，而是综合已经谈过的内容）。用一句直接的陈述句写：绝不要写成"定义性约束："或"要点："这种带标签的旁白；那种写法读起来像填充。这句话是页面上最有价值的一行；永远不要省。

## 何时使用

如何以及何时使用该技能：两拍，几乎总是存在：

- **调用模式。** 说明是你输入还是 agent 触发。用户调用的技能："你通过键入 `/<name>` 来调用它：agent 不会主动触发它。"模型调用的技能："键入 `/<name>`，或者当任务契合时 agent 会自动触发它。"
- **触发边界。** 索引条目："当……时使用它"。当该技能容易与兄弟技能混淆时，加上另一半："对于 <X>，使用 [<sibling>](https://aihero.dev/skills-<sibling>) 代替。"

## 先决条件

可选：只有当技能需要某些前置条件才能工作时才包含；否则整个标题省略。涵盖：**它写入的工作区**（像 `grill-with-docs` 这样的有状态技能会写入 `CONTEXT.md` 和 ADR；`teach` 会构建整个目录：说明它写什么、在哪里写），**前置设置**（`triage` / `to-spec` / `to-tickets` 需要 `setup-matt-pocock-skills` 已经配置好 issue 跟踪器），或**仓库特定工具**。一个可以在任何地方运行的无状态技能没有先决条件：把这一节删掉。

## <自由形式中部>

一到三个简短部分，使用技能*自己的词汇*，让它豁然开朗：选择适合该技能的任意标题：它跑的循环、它产出的工件、它做的分叉、它消除的一个反模式。这里没有规定的标题：技能彼此差异太大，没有统一的模板。

唯一不可妥协的：**突出技能的引导词 / 定义性观念**：`tight` 反馈循环、`deep module`、用可丢弃的代码来回答问题、red-green。它带来双重回报：读者学到了技能*是*什么，也学到了他们日后会用来*想起*它的那个词。

## 常见问题

读者真正会问的关于这个技能的问题，每个加粗，答案写在下方：不要嵌套子标题。

被观察到的问题永远胜过凭空编造的问题，所以在写之前先去找：

- **Wiki。** 如果本机存在 `~/repos/matt/personal-wiki`，那是现有最丰富的来源。它的 `wiki/audience/` 区围绕"受众想要什么、讨论什么、**被什么困惑**"组织：先读 `wiki/index.md` 了解页面的索引，再读与本技能相关的页面。每页都带 `sources:` 回链到原始的 X、Discord、GitHub 和邮件串；wiki 是次要来源，所以引用提问者自己的问题，而不是 wiki 对它的概括。如果该目录不存在则跳过此项。
- **本仓库的 Issues。** `gh issue list --repo mattpocock/skills --search "<skill-name>" --state all`。一个被提过两次的问题，就是页面必须回答的问题。
- **`CHANGELOG.md`。** 任何重命名、移动或行为变更都会产生一个"它去哪了？"，页面必须回答。

搜寻成果单薄时，这一节也可以放读者会自然问到的问题，但**数量要与证据相称**。被频繁讨论的技能值得六条；冷门的值得一两条，或者根本不放。把一个内容稀薄的技能硬凑到内容丰富的技能那样的篇幅，是这一节里堆满没人问过的问题、而虚构的问题什么都教不会读者的方式。

按出现频次排序，最尖锐的优先；该说不好听的就说：一次特别长的盘问会话通常意味着范围太大；一个被要求写自己的技能的模型，写出来的东西又长又空。没什么值得回答时，把整个标题省掉。

## 怎样算成功

几条要点，列出读者能看到的、说明技能在干活的迹象。每条的门槛是读者能在不打开 `SKILL.md` 的情况下自检：是他们自己工作中的信号，或者面前 trace 中的信号。"文档越改越短"过关；"库的 section 和 `template.sh` 字节级一致"是对技能内部的合规检查打着这节的旗号。在迹象明确时包含；迹象含糊时把标题省掉。

## 它的定位

每页必出现。用一两句话把技能放入系统中：

- **角色。** 直接命名：**链步骤**（`grill-with-docs → to-spec → to-tickets → implement → code-review`），**一次性设置**（`setup-matt-pocock-skills`），**定期维护**（`improve-codebase-architecture`，"每几天一次"），或**可随时取用的独立工具**（`diagnosing-bugs`、`prototype`、`handoff`）。独立工具的地图用一句诚实的话即可：远胜于把这一节省略。
- **邻居。** 一到两个重要的兄弟技能，每个带一个 because 从句，使用绝对链接。
- **地图。** 指向 [ask-matt](https://aihero.dev/skills-ask-matt)，即整个集合的路由器，让本页保持为一个节点，而不必重画整张图。

## 约定

- 解释**为什么**，而不是过程。页面用来定位技能并交代其使用场景；它从不复现 `SKILL.md` 中的步骤或模板转储：选择工具的人不需要操作手册。
- **永远不要点名作者。** 这是一份技术文档，而不是"谁说了什么"的记录。"Matt 说过"、"Matt 自己的回答"、"他的观点是"、引用的回复：全部去掉。问题搜寻中得到的发现值得保留；它的归属不必保留。把内容作为关于技能的一句直接陈述（"修复是一条直接的指令：……"，"区分最终落在会话数上"）并去掉框架。读者在决定是否使用工具；观点无论是否归属，分量都一样，而带归属的观点在立场变化的那一刻就过时了。引用*用户*仍然没问题："一位用户报告……"是关于技能在野外的证据，可以保持匿名。
- 使用技能的**引导词**（_seam_、_deep module_、_tracer bullet_），让页面和技能说同一种语言。
- **在 [AI Coding Dictionary](https://www.aihero.dev/ai-coding-dictionary) 有词条时使用其词，并链接页面上的首次出现。** Dictionary 是 AI 编码的官方词汇：_context window_、_subagent_、_harness_、_primary source_、_agent mode_。优先用它的词，而不是你造的同义词。把每个词在页面上的首次出现链接到 `https://www.aihero.dev/ai-coding-dictionary/<slug>`（slug 是该词的小写形式，非字母数字转为连字符：_context window_ → `context-window`），后续出现不再链接。仅在该词在本页携带 dictionary 的含义时链接：领域*模型*、背景*上下文*或身份验证*token* 是另一个词恰好撞名。永远不要在标题、代码 span 或已有链接中链接，也不要把指向本仓库某个技能名称而非概念的词链接起来。要看完整词表，如果本机存在 `~/repos/ai/ai-coding-dictionary/dictionary/` 就读它：一个词一个文件，文件名*就是*该词：否则读 [mattpocock/dictionary-of-ai-coding](https://github.com/mattpocock/dictionary-of-ai-coding)，无论如何它都是事实的源头。
- **分支走表格或列表，绝不走段落。** 当页面要给出一个选择：技能可以产出的两份工件、触发它的四种情况、边界处的五种选项：读者在扫视，寻找匹配自己处境的那一行。段落逼着读者读完全文才能找到。简短的 markdown 表（左列条件，右列动作）或带点列表让人一眼就看清。该规则适用于任何出现分支的地方，最常见于 `## 何时使用` 和自由形式中部。
- 让页面本身保持低负载。它是关于*低认知负载*技能的文档；装饰（多余的标题、重复链接）正是它反对的东西。

## 完成判定

- 页面存在于 `docs/<bucket>/<name>.md`，重命名或 bucket 迁移后没有残留的旧页面。
- 页面不带来源链接，也不自己写安装命令。
- `## 它的作用` 以平铺直叙的散文陈述了定义性约束，而不是带标签的旁白。
- 页面不点名作者、不引用作者：每条断言都靠自身站立。
- `## 何时使用` 陈述了调用模式和触发边界。
- `## 它的定位` 命名了角色，并链接到 `ask-matt`。
- 先决条件（工作区、前置设置、工具）在存在时陈述，在不存在时把这一节省掉。
- 中部展示了引导词。
- 页面用到的每个 AI Coding Dictionary 词都按 dictionary 的写法拼写，且首次：只有首次：链接到 dictionary 条目。
- 每个多路分支都是表格或列表，而不是读者必须通读的段落。
- 搜寻真实问题的工作已经做过：wiki、issues、changelog：`## 常见问题` 与证据相称，不是为了和更丰富的技能页面齐平而硬塞。
- `## 怎样算成功` 的每条要点都能在不打开 `SKILL.md` 的前提下被检验。
- 各部分按模板中的顺序出现。
- 每个链接都是绝对的，且每个都能解析。
