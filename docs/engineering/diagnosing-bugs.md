## 它的作用

`diagnosing-bugs` 对一个棘手的 bug 或性能回退运行六阶段诊断：构建复现（repro）、最小化它、给假设排序、插桩、带回归测试修复、清理。

在存在**紧**反馈回路之前，它不会让代理形成任何理论——一条具名的命令，已经跑过一次，在*这个* bug 上变红、修复后变绿。一个拿到 bug 报告的编码代理的默认行为是读代码然后猜；这个技能阻止这一点。如果不存在能变红的命令，就没有第 2 阶段。这唯一的一道闸门就是这个技能存在的意义。它之后的一切——二分、假设检验、插桩——在信号存在之后都是机械性的。

## 何时使用

键入 `/diagnosing-bugs`，或者当任务合适时代理会自己使用它——它由模型调用，遇到"诊断"/"调试这个"或"某样东西坏了、抛异常、失败、变慢"的报告就会触发。

在难啃的场合使用它：一眼看不穿的 bug、间歇性的偶发失败（flake）、在两个已知良好状态之间悄悄溜进来的回退。它刻意很重，对于你想一条消息就得到答案的问题，它是错误的工具。

| 你的情况 | 去哪里 |
| --- | --- |
| 一个你能用症状描述的具体缺陷 | 这个技能 |
| 一个慢端点，或一个知道前后对比的时序回退 | 这个技能——它有性能分支（先量基线，再二分） |
| "这个代码库的瓶颈在哪里？"——没有具体症状 | 不是这个技能。它诊断一个已知的失败，它不做审计 |
| 一份来自他人的原始 bug 报告，尚未确认或整理 | 先走 [triage](https://aihero.dev/skills-triage) |
| 回答设计问题的一次性代码，而不是追查缺陷 | [prototype](https://aihero.dev/skills-prototype) |
| 测试先行地构建一个计划中的行为 | [tdd](https://aihero.dev/skills-tdd) |
| 不存在能把 bug 锁定的好接缝 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)——这个技能会自己移交到那里 |

## 紧回路就是这个技能

第 1 阶段得到了不成比例的投入，因为它是唯一困难的阶段。技能给出了一架构建回路的阶梯，大致按偏好顺序：

1. 在任意能触达 bug 的接缝处写一个失败的测试。
2. 针对运行中的 dev server 的 curl 或 HTTP 脚本。
3. 带 fixture 输入的 CLI 调用，与已知良好的快照做 diff。
4. 断言 DOM、控制台或网络的无头浏览器脚本。
5. 重放捕获——保存的请求、payload 或事件日志，隔离地跑过代码路径。
6. 一次性 harness：系统的最小子集，一次函数调用。
7. 属性或 fuzz 循环，针对"有时输出错误"。
8. 可以交给 `git bisect run` 的二分 harness。
9. 差分循环——同样的输入，旧版本对新版本。
10. 一个[人在回路（human-in-the-loop）](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop)的 bash 脚本，最后的办法。技能为此随附 `scripts/hitl-loop.template.sh`：代理运行脚本，你在终端里跟随提示，你的回答作为可解析的输出回来。

*一个*回路不是目标。**紧**才是：快（秒级）、确定（每次运行同样的裁决）、锐利（断言你的确切症状，而不是"没崩溃"）、可无人值守地由代理运行。一个 30 秒的偶发回路比没有强不了多少。对于只是偶尔出现的 bug，目标不是干净的复现，而是**更高的复现率**——循环触发、并行化、加压、注入 sleep，直到偶发率高到可以对着它调试。

当它确实构建不出来时，指示是停下来、明说、列出尝试过的东西，并向你要[环境（environment）](https://www.aihero.dev/ai-coding-dictionary/environment)访问权、一个捕获的工件、或添加临时插桩的许可。它不应照旧继续假设。

## 阶段之间的闸门

这些阶段是闸门，不是清单。每一道都拒绝打开，直到某件具体的事为真。

| 闸门 | 必须为真的事 |
| --- | --- |
| 进入第 2 阶段 | 一条具名的命令，已经运行并连同输出一起粘贴，能在该 bug 上变红 |
| 进入第 3 阶段 | 复现已被复现*且*最小化——剩下的每个元素都是承重的 |
| 进入第 4 阶段 | 存在 3–5 个已排序、可证伪的假设，每个都陈述自己的预测，在任何一个被测试之前展示给你 |
| 进入第 5 阶段 | 探针映射到具体的预测，一次一个变量，每条调试日志都带 `[DEBUG-a4f2]` 风格的标签，让清理就是一次 grep |
| 完成 | 原始复现不再复现，插桩已移除，被证明正确的假设写进了提交消息 |

第 5 阶段有一个值得知道的逃生门。回归测试在修复之前写，但仅当存在**正确的接缝**时——一个测试能在调用点按真实 bug 模式运行的接缝。当唯一可用的接缝太浅时，技能被告知要明说，而不是写一个给出虚假信心的测试。那个缺失本身就是发现，也正是把事后分析路由到 `improve-codebase-architecture` 的东西。

## 常见问题

**我只想要一个直接答案的快速问题上，它也会触发。**
这是这个技能被报告最多的问题，而且是真的。尤其在 GPT-5.6-Sol 上，用户报告它在一个平铺直叙的问题描述上就触发了："模型反而触发了相当正式的 diagnosing-bugs 技能。然后它开始构建复现场景——常常构建一个价值有限的模拟场景——然后才给我回答或建议。这导致相当大的回复延迟。"有四个人在 [issue #578](https://github.com/mattpocock/skills/issues/578) 上报告了同样的形态。被接受的修复是先从更轻的方式开始，只在问题值得时才升级到更重的方式，但那个变更还没落地。技能是按 Claude Code 的调用行为校准的；激活阈值更低的[模型（model）](https://www.aihero.dev/ai-coding-dictionary/model)会过度触发它。在它升级之前，实际的办法是说出你想要什么（"直接回答，别诊断"），或者在你的 [harness](https://www.aihero.dev/ai-coding-dictionary/harness) 里为它禁用模型调用。

**我能把它指向一个代码库，问性能问题出在哪里吗？**
不能。它诊断一个你已经能命名的失败。它的性能分支针对有症状的回退——先建立基线测量，再二分，先测量后修复——不是主动扫描。主动版本的技能曾被[提议并关闭](https://github.com/mattpocock/skills/issues/431)；目前没有技能做这件事。

**它会在写修复之前停下来问我吗？**
不会。只有第 3 阶段有人的检查点——排序后的假设清单在任何一个被测试之前展示给你，而如果你不在，它会按自己的排序继续。插桩和修复之间没有闸门，所以代理可以在你同意它的根因之前就开始写代码。[Issue #124](https://github.com/mattpocock/skills/issues/124) 要求那道闸门，仍然开着。如果你想要它，在调用技能时说出来。

**我已经在这份 bug 报告上跑过 `/triage` 了。这又是一遍同样的工作吗？**
部分是，而且两个技能都不承认这一点。正如一位读者所说："Triage 的第 3 步本质上是 diagnosing-bugs 第 1–2 阶段的一个浅层、有边界的实例，但两份文件都没提到对方。"Triage 做一个有边界的"这真的是 bug 吗、表面是什么"的检查；这个技能做彻底版。先跑 triage 不是浪费——它的验证常常给你第 1 阶段的大部分原材料——但在这里要预期重新做一遍，而且预期没有任何交叉引用会告诉你这一点。

**它粘贴的复现输出会泄漏秘密吗？**
可能。技能要求代理粘贴调用及其输出，并索取 HAR 文件、日志转储、核心转储之类的工件。这些都不会按指示脱敏。[Issue #674](https://github.com/mattpocock/skills/issues/674) 提出的恰恰是这一点——凭据、令牌、cookie 和个人数据搭车进入聊天、issue 或 PR——并提议一道脱敏护栏。它开着、未实现。暂时把脱敏当成你的工作，尤其是输出要去任何公开地方之前。

**我的安全扫描器把这个技能标为高风险。**
Snyk 会标它，而这个标记是误报。它是整个集合里唯一随附可执行 shell 脚本（`hitl-loop.template.sh`）并带"运行它"和"curl dev server"指示的技能。随附的 `.sh` 加运行指示加出站 HTTP，足以绊倒静态扫描器。脚本本身大约 30 行 `read -r -p` 提示，暂停等待人类输入。扫描器评的是能力表面，不是被证实的漏洞。

**`/diagnose` 怎么了？**
v1.0.0 里改名为 `/diagnosing-bugs`。旧名字已经不存在了。任何链接着 `/diagnose` 的东西——包装技能、保存的提示词——都需要更新。

## 怎样算成功

- 在它给出任何理论之前，它向你展示一条命令和它的红色输出。如果理论先到，技能就没在运行。
- 它复现的失败是你报告的那个，不是它路上发现的某个相近的。
- 它在开始猜之前缩小复现，并且能告诉你为什么剩下的每一块都是承重的。
- 在任何一个假设被测试之前，你看到 3–5 个排序的假设，每个都带着你能证伪的预测。
- 它加的每条调试日志都带 `[DEBUG-a4f2]` 之类的标签，而它宣布完成时，grep 那个标签结果为空。
- 提交或 PR 消息点名了哪个假设是对的。
- 当它无法用测试锁定 bug 时，它直说，而不是写一个浅的测试。

## 它的定位

`diagnosing-bugs` 是一个随时可取的独立技能。某样东西坏了时你切入它，修复和它的回归测试就位时你切出；它不持有状态，不需要任何前置设置。[ask-matt](https://aihero.dev/skills-ask-matt) 会把"某样东西坏了"路由到这里。

两个邻居很重要。[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 在真正的发现是"代码没有能锁定 bug 的接缝"时接收[移交（handoff）](https://www.aihero.dev/ai-coding-dictionary/handoff)——这个推荐在修复就位之后做出，那时信息更多。[triage](https://aihero.dev/skills-triage) 在它上游，承接来自他人的原始报告形式的 bug，并对同样的前两个阶段做一个更浅的版本。
