## 它的作用

`diagnosing-bugs` 对一个棘手的 bug 或性能回退运行六阶段诊断：构建复现（repro）、最小化它、给假设排序、插桩、带回归测试修复、清理。

在存在一个**紧**的反馈回路之前，它不会让代理形成任何理论——一条具名的命令，已经跑过一次，在*这个* bug 上变红、修复后变绿。一个拿到 bug 报告的编码代理的默认行为是读代码然后猜；这个技能阻止这一点。如果不存在能变红的命令，就没有第 2 阶段。这道闸门就是这个技能存在的意义。它之后的一切——二分、假设检验、插桩——在信号存在之后都是机械性的。

## 何时使用

键入 `/diagnosing-bugs`，或者当任务合适时代理会主动使用它：它由模型调用，遇到"diagnose"/"debug this"，或某样东西坏了、抛异常、失败、变慢的报告就会触发。

在硬骨头面前使用它——一个一眼看不穿的 bug、一个间歇性的 flaky 测试、一个在两个已知良好状态之间悄悄溜进来的回退。它被刻意做得很重，对那种想用一条消息就答完的问题来说是错的工具。

| 你的情况 | 去哪里 |
| --- | --- |
| 一个你可以描述为症状的具体缺陷 | 这个技能 |
| 一个慢端点或有明确前后对照的时序回退 | 这个技能：它有一条性能分支（先量基线，再二分） |
| "这个代码库的瓶颈在哪？"，没有具体症状 | 不是这个技能。它诊断一个已知故障，不做审计 |
| 一份来自他人的、还没确认或整理的原始 bug 报告 | 先 [triage](https://aihero.dev/skills-triage) |
| 为回答一个设计问题而写的、用完就扔的代码，不是为了追缺陷 | [prototype](https://aihero.dev/skills-prototype) |
| 为构建一个计划中的行为而测试先行 | [tdd](https://aihero.dev/skills-tdd) |
| 没有合适的接缝能把这个 bug 钉死 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)：这个技能自己会交接到那里 |

## 紧回路就是这个技能

第 1 阶段占了不成比例的精力，因为它是唯一一个真正难的阶段。技能给出一组构建回路的方法，大致按优先顺序排列：

1. 一条失败的测试，无论接缝在哪，只要能触及 bug。
2. 针对运行中的 dev server 的一条 curl 或 HTTP 脚本。
3. 一条带 fixture 输入的 CLI 调用，对照已知良好的快照做 diff。
4. 一条无头浏览器脚本，对 DOM、console 或网络做断言。
5. 一段重放：一条保存下来的请求、payload 或事件日志，被单独跑过代码路径。
6. 一个用完即扔的 harness：最小子集的系统，一次函数调用。
7. 一条属性或 fuzz 循环，针对"有时输出不对"。
8. 一段二分 harness，可以交给 `git bisect run`。
9. 一条差分回路：同一输入，老版本对新版本。
10. 一条[人在回路（human-in-the-loop）](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop) bash 脚本，最后的手段。技能自带 `scripts/hitl-loop.template.sh` 供此用途：代理跑脚本，你在终端里跟着提示走，你的回答以可解析的输出回传。

*有*一条回路不是目标。**紧**才是：快（秒级）、确定（每次跑同样结论）、锐（断言的正是你的症状，不是"没崩"），并且代理可以无人值守地跑。一条 30 秒的 flaky 回路比没有也好不了多少。对于那种只在某些时候出现的 bug，目标不是干净的复现，而是**更高的复现率**：循环触发条件、并行、加压、注入 sleep，直到 flaky 率达到足以对照调试的水平。

当它真的搭不出回路时，它被指示停下并说"不行"，列出它试过的东西，向你要[环境（environment）](https://www.aihero.dev/ai-coding-dictionary/environment)访问、一份捕获的工件，或临时插桩的许可。它不应该硬着头皮去猜。

## 阶段之间的闸门

这些阶段是闸门，不是清单。每一道都拒绝打开，直到某个具体条件为真。

| 闸门 | 必须为真的条件 |
| --- | --- |
| 进入第 2 阶段 | 一条具名的命令，已经跑过并贴出了它的输出，它能在这个 bug 上变红 |
| 进入第 3 阶段 | 复现已被复现*且*被最小化：剩下的每一项都是承重的 |
| 进入第 4 阶段 | 存在 3–5 条排过序、可证伪的假设，每条都陈述它的预测，且在测试任何一条之前展示给你 |
| 进入第 5 阶段 | 探针对应具体的预测，一次一个变量，每条 debug 日志都打成 `[DEBUG-a4f2]` 这种样式，让清理变成一次 grep |
| 完成 | 原始复现已经不再复现，插桩已清理，且猜对的那条假设被写进了 commit message |

第 5 阶段有一条值得了解的逃生口。回归测试在修复之前写，但只有在存在一个**正确的接缝**时才能写：测试能在这个 bug 模式真实发生的调用点上锻炼它。当唯一可用的接缝太浅时，技能被告知跳到一个浅一些的回归测试，并记录这个权衡——这条规则还比较新，被报告会偶尔压不住。

## 常见问题

**对一个简单的 bug 来说它太重了。**

普遍的抱怨，特别是这个技能是被模型调用的。它用六阶段门控跑哪怕简单的 bug，这是被刻意做重的。已知未修复（[#578](https://github.com/mattpocock/skills/issues/578) 上有同形态的讨论）。大家接受的修法是先以较轻的方式上手，只在问题真的需要时再升级到较重的方式，但这个改动还没落进来。技能是按 Claude Code 的调用行为校准的；一个激活阈值较低的[模型（model）](https://www.aihero.dev/ai-coding-dictionary/model)会过度触发它。在它升级之前，实际的修法是把你要的明说出来（"就答这个，别诊断"），或者在你的 [harness](https://www.aihero.dev/ai-coding-dictionary/harness) 里关掉它的模型调用。

**我能把它指向整个代码库问性能问题在哪吗？**

不能。它诊断一个你已经能说出来的故障。它的性能分支是为有症状的回退准备的（先量基线测量，再二分，先量再修），不是为前瞻性扫描。前瞻性版本的技能被[提出又关掉了](https://github.com/mattpocock/skills/issues/431)；目前没有这样的技能。

**它会在写修复之前停下来问我吗？**

不会。只有第 3 阶段有人工检查点：排过序的假设清单在测试任何一条之前展示给你，如果你不在它就按自己的排序继续走。插桩和修复之间没有闸门，所以代理可能在你还没同意它的根因之前就开始写代码。[Issue #124](https://github.com/mattpocock/skills/issues/124) 提出了这道闸门，仍然是开放的。如果你想要它，在调用技能时说出来。

**我已经在 `/triage` 里跑过这份 bug 报告了。这是同一份工作吗？**

部分是，而且两个技能都不承认。如一位读者所说："Triage 的第 3 步本质上是 diagnosing-bugs 第 1–2 阶段的一个有界浅实例，但两份文档都不提对方。"Triage 做一个有界的"这真的是个 bug 吗、它的表面是什么"的检查；这个技能做的是彻头彻尾的版本。先跑 triage 不是浪费——它的验证常常能给你第 1 阶段的大部分原料——但要预期在这里重做一次彻底的，并且不会有交叉引用告诉你这件事。

**它贴出来的复现输出会不会泄漏密钥？**

可能会。技能让代理贴出调用本身及其输出，并向它索要像 HAR 文件、日志转储、core dump 这样的工件。这些东西没有任何脱敏指示。[Issue #674](https://github.com/mattpocock/skills/issues/674) 正是提的这个（凭据、token、cookie 和个人数据随输出进入聊天、issue 或 PR），并提出了一道脱敏护栏。它是开放的、未实现的。眼下脱敏当作你的事，尤其是在输出要流到任何公开场合之前。

**我的安全扫描器把这个技能标为高风险。**

Snyk 确实标了，但标的是误报。它是整个技能集合里唯一一个自带可执行 shell 脚本（`hitl-loop.template.sh`）并附有运行指令和向 dev server 发起 curl 指令的技能。自带的 `.sh` + 运行指令 + 出站 HTTP 就足以绊倒一个静态扫描器。脚本本身大约 30 行 `read -r -p` 提示，停下来等人工输入。扫描器在打分的是能力面，而不是已被证实的漏洞。

**`/diagnose` 怎么了？**

在 v1.0.0 改名为 `/diagnosing-bugs`。旧名字已不复存在。任何链式使用 `/diagnose` 的东西（一个 wrapper 技能、一份保存的提示词）都需要更新。

## 怎样算成功

- 在它给出任何一条理论之前，它先给你一条命令和它的红色输出。如果理论先到，说明这个技能没在跑。
- 它复现的是你报的那个失败，不是它在路上顺手发现的某个邻居。
- 它在开始猜测之前先把复现缩小了，并且能告诉你剩下的每一块为什么是承重的。
- 在任何一条假设被测试之前，你看到的是一份 3–5 条的、有序的假设清单，每条都带着一条你可以证伪的预测。
- 它加的每一条 debug 日志都带着像 `[DEBUG-a4f2]` 的 tag，等它宣布 done 时，grep 这个 tag 返回为空。
- commit 或 PR 信息里点名了哪条假设是对的。
- 当它没法用一条测试钉住这个 bug 时，它会直说，而不是写一条浅的糊弄过去。

## 它的定位

`diagnosing-bugs` 是一个随时可调用的独立工具。当某样东西坏了你就钻进它，修好回归测试后就退出；它不持有任何状态，也不需要任何先行的设置。[ask-matt](https://aihero.dev/skills-ask-matt) 会把"某样东西坏了"路由到这里。

有两个邻居要紧。[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 在真正的发现是代码没有接缝能钉住 bug 时接手[交接（handoff）](https://www.aihero.dev/ai-coding-dictionary/handoff)；这条建议是在修复落定之后、掌握更多信息时做出的。[triage](https://aihero.dev/skills-triage) 在那些作为他人原始报告到来的 bug 面前坐在它的上游，做同一份前两个阶段的浅版本。
