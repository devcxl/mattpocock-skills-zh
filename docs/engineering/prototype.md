## 它的作用

`prototype` 写出**回答某个问题的一次性代码**——这个状态模型感觉对吗，或者这个界面应该长什么样。问题在前，并决定其后一切事物的形状；一个回答了错误问题的原型是纯粹的浪费，无论它看起来多好。

一次性是对代码*如何写*的约束，不是销毁它的承诺。没有测试、没有超出让它跑起来的错误处理、没有抽象、没有持久化——因为那些都无助于你学到你想学的唯一那件事。幸存下来的是答案，折进真实代码里，以及原型本身，停在 main 之外的分支上，作为答案来源的证据。

## 何时使用

键入 `/prototype`，或者当任务合适时[代理（agent）](https://www.aihero.dev/ai-coding-dictionary/agent)会自动使用它。

当你撞上一个无法靠对话敲定的问题时立刻使用它——一个边界情况你脑内装不下的状态机、一个不看到三个版本并排就想象不出的界面。[盘问（grilling）](https://www.aihero.dev/ai-coding-dictionary/grilling)会话恰恰在这些问题上膨胀：代理换着说法、你猜、范围膨胀去填满不确定性。停止盘问，构建一次性版本，看一眼，然后一行话回答。如果相反，某个已构建的东西行为异常、你想知道为什么，用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)——原型探索的是该构建什么，不是为什么已构建的东西坏了。

你也会不自觉地到达这里。[wayfinder](https://aihero.dev/skills-wayfinder) 会在它的地图上归档 `prototype` 决策 [tickets](https://www.aihero.dev/ai-coding-dictionary/ticket)，做一个 ticket 就是这个技能。

## 两个分支

问题挑选分支，而分支产出截然不同的工件：

- **"这个逻辑/状态模型感觉对吗？"**——一个**可共享的 HTML 文件**。一个自包含页面，无构建、无服务器，双击就能打开。它带一个带标签的状态面板，每次点击后重新渲染；自由操作按钮，可以任意顺序戳模型；以及带标签页的**引导式走查（guided walkthroughs）**——每个标签一个场景，下面配着按顺序要按的按钮。所有东西都用领域语言标注，所以你可以把它交给设计师、PM 或领域专家，让他们自己感受模型。页面背后的逻辑是一个小的纯模块——一个 reducer、一台状态机、一组函数——保持与 DOM 干净分离，这样验证过的版本可以直接提进真实代码。
- **"这应该长什么样？"**——同一条路由上的几个**截然不同**的 UI 变体，可以从浮动底栏和 `?variant=` URL 参数切换。变体必须在结构上分歧，而不是颜色；三个微调的卡片网格是墙纸，不是原型。它们尽可能渲染在真实页面里，对着真实数据和真实密度，因为在真空中评判的变体看起来总是没问题。

两者都把状态留在内存里、开始时无需思考、每一步之后展示给你完整状态。当你发现自己开始加固其中某一个——加测试、接真实数据库、为一个以后可能想要的情况做泛化——你就已经停止原型制作了。

## 原型是一手来源

一个完成的原型留下两样东西，它们去往不同的地方。

**答案**——裁决加上它所敲定的问题——被持久地捕获：一条提交消息、一个 ADR、实现 issue。这是主分支保留的东西，折进真实代码里。

**原型**是答案来自的可运行证据，它不被删除。它也不属于 main——那里没有需要维护的东西，而且它烂得快——所以它被提交到 main 之外的一次性 `prototype/<name>` 分支，永不合并，实现 issue 上留一个指向该分支的[上下文指针（context pointer）](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。Main 保持干净；探索保持可找到、可被下一个接手工作的人重新运行。

## 常见问题

**等等——原型不是应该被删掉吗？**
不再是了。它曾经是：构建它、留下答案、扔了代码。对那做法最尖锐的反对从来不是关于速度——而是*下一个[会话（session）](https://www.aihero.dev/ai-coding-dictionary/session)谁接手工作，他们有什么可依据？*原型的散文摘要会丢失让它有说服力的东西。所以原型现在被当作[一手来源（primary source）](https://www.aihero.dev/ai-coding-dictionary/primary-source)：它落在 main 之外的 `prototype/<name>` 分支上，实现 issue 指向它。改变的是代码住哪里，不是纪律——它仍然永不合并进 main。

**它以前会构建一个终端应用。那去哪了？**
逻辑分支现在改为产出一个可共享的 HTML 文件。终端应用只能被克隆了仓库、装了运行时的人驱动，而这恰恰排除了原型需要其意见的人——设计师、PM、知道状态模型本该意味着什么的领域专家。一个双击打开、经得起被邮件转发的自包含文件，可以被任何人驱动。底下的纯逻辑模块不变，仍然是要提进真实代码的部分。

**一个代理在我本该实现的时候叫我 `/prototype`。**
已知，而且这是一个命名问题。`prototype` 是一个通用、讨喜的词，一个不了解流程的代理会把它读成 tickets 存在之后"显然的下一步"，所以它会被按名字推荐，哪怕设计早已在对话里完全敲定。如果你已经知道要构建什么，下一步是 `/implement`，按 ticket 来。只有当某个具体的设计问题真正悬而未决、且对话解决不了时，才伸手拿原型。

**我应该在生产功能构建之前先把整个应用原型化——比如，向潜在客户演示？**
那是穿着这个技能名字的另一件工件。这里的原型被限定在一个问题上，而"整个应用是什么？"不是一个问题。全应用原型没有自然的停止点，所以它会靠惯性变成生产应用：清理环节永远不会发生，而且在原型规则下写的代码——没有测试、没有错误处理——最终会出现在用户面前。如果你需要一个销售演示，刻意把它当演示来构建，并明确其中没有一样是生产代码。如果你需要敲定一个设计问题，把它裁到那个问题。

**我怎么在它自己的会话里运行它？**
原型住在自己的目录里，产生大量你不想留在提问线程里的[上下文（context）](https://www.aihero.dev/ai-coding-dictionary/context)，所以到别处运行它，只把答案带回来。[handoff](https://aihero.dev/skills-handoff) 是双向的桥。

**这难道不是烧 tokens 最快的办法吗？**
可能是，如果你把本可靠对话回答的问题原型化，或者让一个原型蔓延过整个功能。重要的对比不是 tokens 对零；而是 [tokens](https://www.aihero.dev/ai-coding-dictionary/token) 对构建了错误的状态模型、等到它有生产调用者之后才发现。把问题收窄、运行缩短，花费就保持相称。

## 怎样算成功

- 你能用一句话说出原型存在是为了回答什么问题——而且它写在演示的顶部，不只是在你脑子里。
- 一个不读代码的人能驱动逻辑演示。他们打开文件、在一个走查标签里按按钮、用自己的话描述所见。
- 有人说"等等，那不应该可能"或"咦，我以为 X"。那是*想法*里的 bug，而这正是全部意义所在。
- UI 变体在布局和信息层级上分歧，而不只是颜色和文案——你得到的反馈是"B 的头部加 C 的侧边栏"。
- 它在一口气内被回答。如果一天之后你还在构建它，问题太大了；拆开它。
- 结束时，main 包含决策、不含任何原型，实现 issue 指向仍持有它的那个分支。

## 它的定位

`prototype` 是一个**随时可取的独立技能**——你切入它敲定一个设计问题，然后切出——它也是另一个技能运转其上的机制。

它最大的消费者是 [wayfinder](https://aihero.dev/skills-wayfinder)。一张 wayfinder 地图由**决策 tickets** 组成，而 `prototype` 是一个 ticket 可以是的四种类型之一：当阻塞问题是"这应该看起来什么样"或"这应该怎么表现"、任何讨论都解决不了时使用的那一种。Wayfinder 通过造出可以反应的具体东西来提高一场模糊讨论的分辨率，而这个技能就是那具体东西被构建的方式。一个原型 ticket 由答案解决，原型作为资产从地图链接出来。

其他邻居在它的上游和下游。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答可盘问的问题；不可盘问的来这里，一行话的回答回到访谈里。下游，一个验证过的状态模型或 UI 方向成为 [to-spec](https://aihero.dev/skills-to-spec) 的敲定输入，后者可以直接内联原型产出的决策密集片段，而不是用散文描述它。其他任何情况，[ask-matt](https://aihero.dev/skills-ask-matt) 会带你路由整个集合。
