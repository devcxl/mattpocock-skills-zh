# to-tickets

接收一个计划、Spec 或对话，生成一组 ticket——采用 tracer-bullet（垂直切片）方式，每个 ticket 标明**阻塞**它的其他 ticket。

分类标签词汇表应当已经提供给了你——如果没有，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从对话上下文中已有的内容开始。如果传入了某个引用（Spec 路径、Issue 编号或 URL），获取它并阅读其完整正文和评论。

### 2. 探索代码库（可选）

如果你尚未探索代码库，请先了解当前代码的状态。在整个 ticket 的标题和描述中使用项目的领域术语词汇表，并尊重你所涉及区域内的任何 ADR。

寻找预先重构代码的机会，使实现变得更加容易。"先让改动变得容易，再做容易的改动。"

### 3. 起草垂直切片

将工作分解为 **tracer bullet**（追踪子弹）式 ticket。

每个切片提供一个狭窄但**完整**的、贯穿每一层（schema、API、UI、测试）的通路——是垂直切片，而非单层的水平切片。完成后的切片可以独立演示或验证。每个切片应适合放入一个全新的上下文窗口。任何预先重构应首先完成。

对于每个 ticket，标明**阻塞**它的内容——即必须先完成才能开始此 ticket 的那些 ticket。没有阻塞依赖的 ticket 可以立即开始。

**大范围重构会破坏垂直切片。** 当某个机械性改动（如重命名列、更改共享类型结构）的**影响范围**横跨整个代码库，一次编辑会破坏数千个调用点，且没有任何垂直切片能保持通过状态时，不要强行将其塞进 tracer bullet；应通过 **expand-contract（扩展-收缩）** 来编排。先扩展：在保留旧形式的同时添加新形式，确保没有任何问题。然后按影响范围顺序（按包、按目录）迁移调用点，每批作为独立的 ticket，被扩展阶段阻塞，每批之间 CI 保持通过，因为旧形式仍然可用。最后收缩：在所有调用者迁移完成后删除旧形式，作为一个被所有迁移批次阻塞的 ticket。即使各批次无法单独保持通过，也要保持顺序，但建立一个集成分支，最终阻塞一个集成验证的 ticket——只在那里保证通过。

### 4. 获得用户确认

将提议的分解方案以编号列表形式呈现。对于每个 ticket，展示：

- **标题**：简短、描述性的名称
- **被以下 ticket 阻塞**：必须首先完成的 ticket（如果有的话）
- **交付内容**：此 ticket 实现的端到端行为

向用户询问：

- 粒度是否合适？（太粗 / 太细）
- 阻塞依赖关系是否正确——每个 ticket 是否只依赖于真正阻塞它的内容？
- 是否有 ticket 需要合并或进一步拆分？

反复迭代，直到用户批准分解方案。

### 5. 将 ticket 发布到已配置的跟踪器

发布已获批准的 ticket。**发布方式**取决于 `/setup-matt-pocock-skills` 配置的跟踪器——ticket 本身是相同的，只有阻塞依赖关系的表现形式不同：

- **本地文件** → 在仓库根目录下写入一个 `tickets.md` 文件，按依赖顺序（阻塞者优先）列出所有 ticket，每个 ticket 的"被以下 ticket 阻塞"列出其所依赖的标题。使用下面的文件模板。
- **真实的 Issue 跟踪器（GitHub、Linear 等）** → 按依赖顺序（阻塞者优先）为每个 ticket 创建一个跟踪器条目，这样每个 ticket 的阻塞依赖可以引用真实的 ID。如果平台支持，使用跟踪器原生的阻塞/子依赖关系；否则将每个 ticket 的"被以下 ticket 阻塞"设置为阻塞它的跟踪器条目。除非另有指示，应用 `ready-for-agent` 分类标签——这些 ticket 天然适合 agent 认领。

**不要**关闭或修改父级 Issue。

### Ticket 文件模板

```
# Tickets：<工作的简短名称>

对这些 ticket 所构建内容的一句话总结。如果有源 Spec，请引用它。

从**前沿（frontier）**开始工作：任何所有阻塞依赖都已完成的 frontier ticket。对于纯线性链条，即从上到下依次进行。

## <Ticket 标题>

**要构建的内容：** 此 ticket 从用户角度实现的端到端行为——而不是按层的实现列表。

**被以下 ticket 阻塞：** 阻塞此 ticket 的标题，或者"无——可以立即开始。"

- [ ] 验收标准 1
- [ ] 验收标准 2

## <Ticket 标题>

...
```

### Issue 正文模板

```
## 父级

引用跟踪器中的父级 Issue（如果源不是现有 Issue，则省略此项）。

## 要构建的内容

此 ticket 从用户角度实现的端到端行为——而不是按层的实现列表。

## 验收标准

- [ ] 标准 1
- [ ] 标准 2

## 被以下 ticket 阻塞

- 引用每个阻塞 ticket，或者"无——可以立即开始。"
```

无论采用哪种形式，都要避免具体文件路径或代码片段——它们很快就会过时。例外情况：如果某个原型生成的代码比文字更精确地编码了一个决策（如状态机、reducer、schema、类型结构），则在相关决策处内联它，并简要说明它来自原型。只保留决策密集的部分——不是完整的工作演示，只是重要的内容。

每次使用 `/implement` 在 frontier 上处理一个 ticket，在 ticket 之间清空上下文。
