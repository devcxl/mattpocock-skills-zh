## 它的作用

`handoff` 把你正在进行的对话压缩成一份**移交文档（handoff document）**——一个 markdown 文件，写到操作系统的临时目录而不是工作区里——一个新的[代理（agent）](https://www.aihero.dev/ai-coding-dictionary/agent)可以读它来接手工作。

它买到的是**可移植性（portability）**，不是压缩。这让技能比听起来窄。只有当工作必须*旅行*时你才需要文件——到一个新的 [harness](https://www.aihero.dev/ai-coding-dictionary/harness)、一个新目录、一位同事、或一个你想分叉出去的副任务。如果没有什么在旅行，你不需要 handoff：留在[会话（session）](https://www.aihero.dev/ai-coding-dictionary/session)里、`/clear`、一个[子代理（subagent）](https://www.aihero.dev/ai-coding-dictionary/subagent)和 `/compact` 覆盖了普通的阶段结尾情况，而 `/compact` 覆盖它的次数比这个技能多。

## 何时使用

你通过键入 `/handoff` 来调用它——代理不会主动使用它。传一条关于下一个会话要做什么的说明，文档就为它而写。

四种情况是全部触发条件：

| 情况 | 为什么需要文件 |
| --- | --- |
| 更换 harness——Claude → Codex | 新 harness 看不到旧[上下文（context）](https://www.aihero.dev/ai-coding-dictionary/context) |
| 移到不同的目录或仓库 | 原型目录是常见情况 |
| 把工作发给一位同事 | 他们需要能读的东西 |
| 分叉一个阶段中途发现的副任务 | 你继续工作；第二个代理接手分叉 |

其他任何情况——同一个 harness、同一个目录、你[盘问（grilling）](https://www.aihero.dev/ai-coding-dictionary/grilling)完了正要转去实现——`/compact` 才是动作。[ask-matt](https://aihero.dev/skills-ask-matt) 在阶段边界上携带覆盖全部五个选项的有序决策树。

## 分叉是人们跳过的那种用法

技能的描述读起来像会话恢复：写摘要、在这里结束、在那里继续。按那个读法它看起来像一个更差的 `/compact`，所以被略过。分叉案例才值得知道。你**留在自己的会话里**，把积累上下文的副本交给一个并行工作的第二个代理。

这正是绕道 [prototype](https://aihero.dev/skills-prototype) 所用的。你深陷一场设计对话，撞上一个只有可运行的代码才能敲定的问题，而你不想把你建起来的线程花在查明它上。移交给一个原型会话，拿到答案，把答案交回来，并从原始线程引用它。两次穿越，一场活对话，什么都不用重新解释。

阶段边界的五个选项里，有三个保留不同的东西：`/compact` 保留你的意图，`/clear` 什么都不保留，`/handoff` 保留工作移动的能力。

## 什么会旅行，什么不会

文档携带活线程——什么在进行中、为什么、下一步是什么——外加一个**建议技能（suggested skills）**小节，点名下一个代理应该伸手拿什么。秘密在它被写出之前被脱敏。

它刻意不携带任何已经写下来的东西。Specs、计划、ADR、issues、提交和 diffs 按路径或 URL 引用，从不复制。这让文件保持小，也让已敲定的细节保持在一个地方，而不是两个会漂移的地方。

## 常见问题

**Handoff 还是 compact？**
除非有东西在旅行，否则 `/compact`。留在同一个任务上是压缩，不是移交——同一个 harness、同一个目录、你需要保持在回路里，这是阶段边界树大多数日子落下的地方。`/handoff` 的优势不是它摘要得更好；而是结果是一个你能带去 `/compact` 够不到的地方的文件。

**那 compact、clear 和 handoff 的实际区别是什么？**
三样被保留的不同东西。`/compact` 压缩这个上下文，让你在一个新窗口里继续——意图幸存。`/clear` 清空窗口、从零开始——当你身后的一切都可丢弃时是对的，如果不是，它就是单向的。`/handoff` 写一个可移植的文件——工作在搬到别处时幸存。注意三者都把**[一手来源（primary source）](https://www.aihero.dev/ai-coding-dictionary/primary-source)**（如实发生的对话）变成**[二手来源（secondary source）](https://www.aihero.dev/ai-coding-dictionary/secondary-source)**（它的摘要）。继续是唯一不这样的动作，所以它是第一个该被排除的。

**我的 handoff 文件去哪了？**
临时目录，这是这个技能被报告最多的摩擦点：路径长、随操作系统不同、在 Windows 上代理有时要试好几次才找到正确的那个。在继续之前要回路径并保存它。用 temp 是刻意的：handoff 是中转文档，不是你要维护的工件。它也不是持久的——见下一个问题。

**我的 handoff 在会话之间消失了。**
有些环境会在会话之间清空 temp——Codex 是被报告的案例——而 `/private/tmp` 会在重启时清掉。如果下一个会话不会在一小时内开始，或者会在不同的 harness 下开始，文件一写好就自己把它复制到某个持久的地方。文档*指向*的任何东西也一样：一份引用 temp 里其他文件的派发，是下一个代理无法跟随的派发。

**我到底怎么把它交给下一个代理？**
打开新会话，把它指向路径：读这个文件，然后继续。指向文件，而不是把摘要粘进一个 shell 命令——一个含反引号或 `$(...)` 的摘要被插值进 `claude "<summary>"` 时会被弄乱，而常见的失败是无声截断而不是报错，所以新代理从一份悄悄不完整的简报开始。

**这和 `/branch`、`--fork-session` 或内置的 `/handoff` 一样吗？**
类似，不完全相同，而且 `/branch` 在这里不是已发布的技能——`/handoff` 是规范名字。一个 fork 继承上下文的精确副本；这个技能产出一份瞄准所述下一个任务的*定向*压缩，在一个文件里。在 fork 能行的地方——同一台机器、同一个 harness、同一个目录——fork 工作量更少。当目的地是 fork 去不了的地方时，文件胜出。

**什么时候某样东西反而该进 `CLAUDE.md`？**
问它下个月是否还为真。`CLAUDE.md` 是关于项目的常驻上下文，被加载进每个会话，无论相关与否。Handoff 关乎一件进行中的工作，那工作一落地它就死了。老是重新解释的事实是 `CLAUDE.md` 的问题；一件做了一半的任务是 handoff。

**它捕获了什么，没捕获为什么。**
一个公允且被反复提出的批评。两件事有帮助。传参数——告诉它下一个会话是干什么的——这样对*那个*有影响的推理被保留，而不是被压平。以及留意会话从未真正验证过的自信断言："X 没构建"、"Y 完成了"。下一个代理把文档当契约，不会重新检查它，所以一个被写成事实的信念会变成其后一切的错误前提。交出去之前读一遍文档，把你只是假设的东西降级。

**为什么它是技能而不是斜杠命令？**
两者都行；它们适合不同的情况。作为技能，它和这里其他一切走同一条安装路径发布和更新，这正是让它可分享的原因——代理不会自己触发它的约束由它的 frontmatter 设定，而不是由机制设定。

## 怎样算成功

- 文档只是对话的一小部分，specs、issues 和 diffs 以路径和 URL 出现，而不是复制的文本。
- 你能冷读它，不打开原始会话，就知道下一步做什么。
- 新代理开始工作，而不是要你重新解释环境。
- 在分叉案例里，你回来时原始会话还原封不动坐在那里。
- 建议技能小节点名的，正是你自己会伸手拿的那个技能。
- 里面没有密钥、令牌或密码。

## 它的定位

`handoff` 是一个**随时可取的独立技能**，活在会话之间的接缝处，而不是构建链内部——但一条窄缝，诚实地讲，你在阶段边界上用它会比另外四个选项少。它最近的邻居是 [prototype](https://aihero.dev/skills-prototype)，因为原型住在自己的目录里，而出去再回来的往返恰恰是这个技能为之存在的穿越。当你处在一个边界、拿不准是继续、清空、移交、委派还是压缩时，[ask-matt](https://aihero.dev/skills-ask-matt) 携带给那五个排序的决策树——并带你路由集合的其余部分。
