## 它的作用

`to-questionnaire` 把你一个人做不下来的决定变成一份**问卷**：一份 Markdown 文档，交给你缺少信息的那一个人，让他们异步填写，或者你们俩在一次会议里一起过完。

它盘问你的是**发送对象**，而不是主题本身。在这里就主题去访谈你毫无意义：不知道主题正是你向别人请教的原因。所以它只问两件你总能回答的事：这份东西发给谁，以及你希望从他们那里拿回什么：然后把文档里的每一道问题都对准这两者之间的**鸿沟**。

## 何时使用

你通过键入 `/to-questionnaire` 来调用它：[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 不会主动触发它。

在一个决定被卡在"答案只活在另一个人脑子里"的时候就用它：客户、领域专家、握有业务规则的 exec、你不坐在同一支团队的同事。要用哪一个技能，取决于答案到底在哪里：

| 答案在…… | 用 |
| --- | --- |
| 你自己的脑子里，还未被磨利 | [grill-me](https://aihero.dev/skills-grill-me) |
| 代码库里 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 别人的脑子里 | `to-questionnaire` |
| 谁的脑子里都没有：这个问题需要点东西让你反应 | [prototype](https://aihero.dev/skills-prototype) |

常见情况是一次 [grilling](https://www.aihero.dev/ai-coding-dictionary/grilling) session 卡壳了：浮现出来的东西有一些不是你能回答的。在那次对话里跑 `/to-questionnaire`，把那些问题带离现场，等回答回来再继续。

## 发送对象，而非主题本身

访谈是两轮，然后停下。

- **发给谁？** 他们的角色、专业领域、和你的关系。这决定了文档的语气以及它得携带多少上下文：外部客户需要被定向，团队内的同事不需要。
- **你希望拿回什么？** 你独自解决不了的、具体的决策或事实。这变成文档成品被对照的清单：你点名的每一项都会有一道问题对准它。

在那之后就是起草。文件落在当前目录下的 `to-questionnaire-<slug>.md`。没有设置、没有 workspace，也没有任何要配置的东西。

## 这份文档

它被框定为一份**探索性问卷**：你缺上下文，对方有。这种框定决定了它的形状：

- 一行目的，写明取决于它的决定；一节短小的"上下文"，为不在你脑子里的接收者定向。
- 问题按**重要性递减**排序，并在主题分组的 `##` 标题下分组，因为异步意味着你可能只有一次机会。
- 一道问题一个点，绝不复合，下面给一个回答占位符，再加一行"为什么这重要"，仅在问题可能被误读时。
- 明确允许回答"我不知道"：被标记出来的不确定是有用的；像事实一样的自信猜测不是。
- 一个收尾的兜底：还有什么是我们没问但应该知道的？

它刻意不成为的两样东西。它不**分叉**：问题是一个扁平的分组列表，而不是一棵"如果答了 A 就跳过 D"的树。它也不**多收件人**：一次运行产出给一个人的一份文档。

## 常见问题

**它会读我那次 grilling session 并把问题抽取出来吗？**
不是作为它自己的步骤。这个技能没有摄入阶段：它只问发送对象，然后起草。grilling session 之后它之所以好用，是因为你在**同一次对话**里跑它，所以 [session](https://www.aihero.dev/ai-coding-dictionary/session) 已经处于 [context](https://www.aihero.dev/ai-coding-dictionary/context) 之中，起草能从中取材。新开一个 session 再启动它，它对那次 grilling 一无所知：你会在回答"你希望拿回什么？"时把主题重新喂一遍。

**缺失的答案不全在同一个人那里。它能按收件人拆分吗？**
不能。第一步问的是*那位*收件人，单数，整份文档的语气和上下文都是冲着他们的。三个人各拿一部分答案，就跑三次，一次一个人。按学科或角色在单份文档里路由问题是被提过的请求；交付的不是这个。

**问题之间有依赖吗：它会按之前的答案跳过某些节吗？**
不会。问题间依赖的设计被探索过，但没交付。输出是一份静态文档：按主题分组、按重要性递减、每题都活跃。反对意见是公正的：一个 [model](https://www.aihero.dev/ai-coding-dictionary/model) 真的答案之前超过两三个问题就规划得很糟，而一份分叉文档必须在每一个答案之前把所有问题都规划好。

**如果收件人也答不上来呢？**
文档告诉他们直接说。"我不知道"和部分回答是被明确要求的；被标记出来的不确定比猜测更有用，因为一个含糊的回答和一个自信的错误回答一旦回到你的 context 里看起来完全一样。

**它会把东西发出去吗：Slack、issue 跟踪器、邮件？**
不会。它把一份 Markdown 文件写在当前目录里，并把路径告诉你。投递是你的事：粘到一张 [ticket](https://www.aihero.dev/ai-coding-dictionary/ticket) 里、丢进 Slack 线程、附在邮件上，或者在共享屏幕上打开，一起在会议里过完。大家都手工把四种都试过。

**这不就是 `/grill-me` 的批处理模式吗？**
不是，区别值得守住。`grill-me` 已经是**分轮**：一次问完整个前沿，再根据你的回答重算：所以"一次性把所有问题给我"的需求在那里已经被满足了。`to-questionnaire` 走的是另一条维度：不是问题怎么交付，而是答案在谁的脑子里。自己更快地答完是 `grill-me`；从别人那里把答案拿出来是这个。

**我就不能跳过技能直接问 agent 吗？**
可以，而且在这个技能出现之前很多人都这么干过：`OPEN_QUESTIONS.md` 文件、发给客户的电子表格、一张"needs more info"的 ticket 对应每个未答的问题。技能给你两样东西：访谈不会滑到主题上，文档以非技术收件人能真正填写的形式出炉。如果你已经有一份现成的、有效的内部格式，诚实的答案是你不需要这个。

## 怎样算成功

- 它只问收件人和要拿回什么，然后就停。关于主题本身的问题是技能跑偏了。
- 你点名的"要拿回什么"中的每一项都能在文件里追到一道问题。
- 问题读起来是冲着*收件人*所知而问的，而不是把你自己那些没回答的问题原样抄下来。
- 你能把这份文件交给一个不在对话里的人，他们能知道为什么收到，以及最迟何时回复。
- 回来的答案是新 grilling 轮的可用输入，而不是又一份新问题。

## 它的定位

`to-questionnaire` 是一个可随时取用的独立工具。它站在你自己知识的边界上，下一步是另一个人而不是另一个技能：最常发生在流程中途，计划卡在一个不属于你决策的东西上。

它的邻居是 [grill-me](https://aihero.dev/skills-grill-me)，两者按答案住在哪里来划分：grilling 挖的是你自己，问卷挖的是别人。回来的是生料：喂给另一轮 grilling，或者喂给 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)，如果工作是奔着构建去的话。不确定哪个技能适合当下时，[ask-matt](https://aihero.dev/skills-ask-matt) 给你路由。
