# Deepening（深入挖掘）

给定一组浅层模块及其依赖关系，如何安全地让它们变深。本文档预设你已经熟悉 [SKILL.md](SKILL.md) 的词汇：**module**、**interface**、**seam**、**adapter**。

## 依赖类别

在评估一个深入候选时，先对其依赖进行分类。类别决定了深化后的模块如何跨越 seam 进行测试。

### 1. 进程内

纯计算、内存状态、无 I/O。永远可以深化：合并这些模块，直接通过新接口测试。不需要 adapter。

### 2. 本地可替代

依赖具备本地测试替身（PGLite 替代 Postgres、内存文件系统）。只要替身存在就可以深化。深化后的模块在测试套件里跑该替身进行测试。seam 是内部的；模块外部接口上不暴露 port。

### 3. 远程但自有（Ports & Adapters）

跨网络边界的自有服务（微服务、内部 API）。在 seam 处定义 **port**（接口）。深模块拥有业务逻辑；传输机制以 **adapter** 注入。测试用内存 adapter；生产用 HTTP/gRPC/queue adapter。

推荐表述："在 seam 定义一个 port，生产实现 HTTP adapter，测试实现内存 adapter，让逻辑集中在一个深模块中，即使它部署时跨越网络。"

### 4. 真正的外部（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。深化后的模块把外部依赖作为注入的 port；测试提供 mock adapter。

## Seam 纪律

- **一个 adapter 意味着假设中的 seam。两个 adapter 才是真正的 seam。** 除非至少两个 adapter 是合理的（通常是生产 + 测试），否则不要引入 port。单 adapter 的 seam 只是徒增间接层。
- **内部 seam 与外部 seam。** 一个深模块可以既有内部 seam（实现私有，给自己的测试用），也有位于其接口处的外部 seam。不要因为测试用到内部 seam，就把内部 seam 通过接口暴露出去。

## 测试策略：替换，而非叠加

- 浅模块上的旧单元测试，一旦在深化模块的接口处有了测试，就成了废品——删掉。
- 在深化模块的接口处写新测试。**接口即测试面。**
- 测试通过接口断言可观察的输出，而不是内部状态。
- 测试应能扛住内部重构，因为它们描述的是行为，不是实现。如果实现一改测试就得跟着改，那测试就越过了接口在测实现。
