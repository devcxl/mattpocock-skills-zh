# 设计两次（Design It Twice）

当用户希望为选定的深化候选方案探索替代接口时，使用此并行子代理模式。基于"设计两次"（Ousterhout）——你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇——**模块**、**接口**、**seam**、**适配器**、**杠杆**。

## 流程

### 1. 框定问题空间

在生成子代理之前，为选定的候选方案写一份面向用户的问题空间说明：

- 任何新接口都必须满足的约束
- 它依赖的依赖项，以及它们属于哪个类别（参见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的说明性代码草图，使约束具体化——不是方案，只是让约束变得具体的方式

将其展示给用户，然后立即进入步骤 2。用户在子代理并行工作时阅读和思考。

### 2. 生成子代理

并行生成 3 个以上的子代理。每个子代理必须为深层模块提出一个**根本不同的**接口。

为每个子代理提供一份独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、seam 背后是什么）。该简报与步骤 1 中面向用户的问题空间说明无关。给每个子代理一个不同的设计约束：

- 子代理 1："最小化接口——最多 1-3 个入口点。最大化每个入口点的杠杆。"
- 子代理 2："最大化灵活性——支持多种使用场景和扩展。"
- 子代理 3："为最常见的调用方优化——让默认情况变得简单。"
- 子代理 4（如适用）："围绕端口和适配器设计跨 seam 依赖。"

在简报中同时包含 [SKILL.md](SKILL.md) 词汇和 CONTEXT.md 词汇，这样每个子代理的命名与架构语言和项目领域语言保持一致。

每个子代理输出：

1. 接口（类型、方法、参数——以及不变量、顺序、错误模式）
2. 使用示例，展示调用方如何使用
3. 实现隐藏在 seam 后面的是什么
4. 依赖策略和适配器（参见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——杠杆在高处、在何处薄弱

### 3. 展示与对比

依次展示设计，让用户逐一理解，然后用文字对比。从**深度**（接口处的杠杆）、**局部性**（变更集中在何处）和**seam 放置**三个维度进行对比。

对比之后，给出你自己的推荐：你认为哪个设计最强，以及理由。如果不同设计中的元素可以很好地组合，提出一个混合方案。要有主见——用户想要的是强有力的判断，而不是一个菜单。
