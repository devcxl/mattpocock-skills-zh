# 逻辑原型（Logic Prototype）

一个自包含的 HTML 文件——一份**可分享的演示**——让任何人都能通过点击按钮来驱动状态模型。当问题涉及**业务逻辑、状态转换或数据形态**时使用——这类东西在纸面上看起来很合理，只有推过真实用例才会觉得不对劲。

因为只有一个文件、无需安装任何东西，你可以把它交给非开发者——设计师、产品经理、领域专家——让他们亲手感受这个模型。所以它要说他们的语言，而不是代码的语言。

## 什么时候这个形态是对的

- "我不确定这个状态机能不能处理 X 之后 Y 的边界情况。"
- "这个数据模型真的能让我表示……的情况吗？"
- "我想在写 API 之前先感受一下它应该长什么样。"
- 任何需要**按下按钮、观察状态变化**的场景。

如果问题是"它应该长什么样"——走错分支了。用 [UI.md](UI.md)。

## 流程

### 1. 明确问题

写代码之前，先写下你要原型化的状态模型和你要回答的问题。写一段话，放在演示的顶部（一个可见的引言，而不是只有注释）。回答错问题的逻辑原型纯属浪费——把问题写清楚，这样之后可以核对，无论用户是现在看着，还是之后 AFK 回来再看。

### 2. 把逻辑隔离在一个可移植的模块里

把真正的逻辑——回答问题的那部分——放在一个 `<script>` 块里，写成一个小而纯的模块，日后可以直接抽出来放进真实代码库。周围的页面是一次性的；这个模块不是。

正确的形态取决于问题：

- **纯 reducer**——`(state, action) => state`。当 action 是离散事件、state 是单一值时适用。
- **状态机**——显式的状态和转换。当"现在到底哪些 action 是合法的"本身就是问题的一部分时适用。
- **一组操作普通数据类型的纯函数**。当没有隐含的当前状态、只有变换时适用。
- **一个方法表面清晰的类或模块**——当逻辑确实拥有持续的内部状态时。

选择最贴合所问问题的形态，*而不是*最容易接到页面上的形态。保持纯净：不碰 DOM、不碰 `document`、按钮处理器不能伸进模块内部。页面调用它；数据绝不反向流动。这正是原型在自身生命周期之外仍有价值的原因：问题一旦回答，验证过的 reducer / machine / 函数集就能自行升入真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS——没有框架、没有打包器、没有服务器，全部内联，这样双击就能打开，甚至经得起被邮件传来传去。任何人都应该能打开即用。

为非开发者而写。每个标签都用**领域语言**，而不是代码——按钮和状态读起来像业务，而不是像 reducer。用大白话解释正在发生什么。

用清晰的层级从上到下布局：

1. **标题和一行说明**，说明这个演示让你探索什么（第 1 步的问题）。
2. **当前状态**——完整的相关状态，渲染成一个易读的面板（带标签的字段，而不是原始 JSON 转储），每次点击后重新渲染，让变化可见。如果有助于非开发者跟上，就指出刚刚发生了什么变化。
3. **自由试玩按钮**——每个 action 一个按钮，始终可用，任何人都可以按任意顺序摆弄模型。每次点击分派对应的 action 并重新渲染状态。
4. **引导式演练**——一组**场景**，每个标签页一个。每个标签页里有一段简短的白话场景描述——它搭建了什么情境、要留意什么——下面是为该场景排好顺序的**待按按钮**。每一步都是真实的按钮：点击它执行该 action 并进入下一步。开始一个演练会重置到已知的初始状态，这样场景每次都以同样的方式运行。

挑选能展示棘手用例的场景——happy path、一个刁钻的边界情况、一次对"本应非法"之事的尝试——也就是那些在纸面上很难推理的用例。

保持美观但有节制：干净的排版、充裕的留白、一个强调色。没有动画、没有花活——不与状态和按钮抢注意力。

### 4. 交付

把文件发给他们，或替他们打开。他们会随手点过演练、自由试玩；有趣的时刻是当他们说"等等，这不应该可能发生"或"哈，我以为 X 会是那样的"——那些是*想法*里的 bug，而这正是全部意义所在。如果他们想要新的 action 或新场景，就加上。原型是会演化的。

### 5. 留存答案和原型

一旦原型回答了问题，先留存答案，再按 [SKILL](SKILL.md) 描述的方式留存原型。逻辑侧的对应关系：验证过的 reducer / machine / 函数集升入真实模块（决策被吸收）；HTML 外壳随一次性分支一起保留，让原型作为一手来源存在——而且由于它是自包含的单文件，在那里随时可以重新运行。

## 反模式

- **不要添加测试。** 需要测试的原型就不再是原型了。
- **不要接上真实数据库。** 用内存状态，除非问题专门关于持久化。
- **不要泛化。** 别想"万一以后要支持 X 呢"。原型只回答一个问题。
- **不要把逻辑和页面混在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理器，它就不再可移植了。让页面保持为覆盖在纯模块上的薄壳。
- **不要动用框架、打包器或服务器。** 一个收件人双击即开的文件；React 应用或开发服务器会毁掉"可分享"。
- **不要把 HTML 外壳发布到生产环境。** 页面是为人工点击体验优化的。它背后的逻辑模块才是值得保留的部分。
